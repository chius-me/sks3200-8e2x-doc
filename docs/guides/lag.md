# 链路聚合

页面：**高级设置 → 链路聚合**（`/link_aggregation.html?nav=2-4`）。

本页根据 2.0.0.1 的字段写成。没有在设备上真正建立过聚合组，也没有和对端 LACP 握手验证。

## 页面上实际有什么

每个端口一行，外加一个全局「LACP系统优先级」（当时显示 32768）。

| 你在页面上看到的名字 | 选项或范围 | 静态模式下 |
|---|---|---|
| 端口类型（第一列） | 静态、LAG、LACP | 当时全部为静态 |
| 端口类型（第二列，1–65535） | 数值 | 当时为 128，输入框禁用 |
| LACP超时时间 | 短、长 | 当时为短，控件禁用 |
| 聚合组 | 0–15 | 当时为 0，输入框禁用 |
| LAG状态 | 只读 | 随链路亮/灭 |

两个字段都叫「端口类型」是界面原文，不是文档写错。第二列很像其它交换机上的端口优先级，**这是推测**。

聚合组给出 0–15，与部分评测「最多 16 组」相符；组 0 在当时全部禁用，不能据此说已经有业务聚合。

未见：

- 散列算法（源 MAC / 目的 MAC / IP / 端口）
- LACP 主动 / 被动
- 对端系统 ID、对端口、聚合是否同步
- 把聚合口当成一个逻辑口再去选 VLAN 的单独对象

VLAN 仍按物理口 1–10 来选成员。聚合和 VLAN 的先后顺序、聚合口是否继承成员关系，都未验证。

## 三种模式怎么理解

页面没有帮助文本。下面区分「页面字面」和「社区说法」。

| 页面选项 | 能确定的 | 不能确定的 |
|---|---|---|
| 静态 | 当时所有端口都在这一项；后三列控件禁用 | 是否表示「未加入聚合」，还是「静态聚合的一种」 |
| LAG | 字面上像静态聚合 | 是否必须改聚合组号、是否要对端也是静态、如何选散列 |
| LACP | 字面上像 802.3ad | 超时短/长的秒数、主动还是被动、最少几条链路才转发 |

社区评测（针对更早批次，VLAN 界面不同）曾经写过：

- 默认 Static = 无聚合
- LAG = 静态聚合，LACP = 动态聚合
- Short 超时约 3 秒，Long 约 90 秒
- 最多 16 个聚合组

这些数字**没有**在 2.0.0.1 上核对。超时秒数不要当已验证参数用。

## 建议的操作顺序（未跑通）

在 NAS、路由器或对端交换机已经准备好对应聚合的前提下：

1. 下载配置备份。
2. 确认这些口没有在做镜像目的口，也尽量先理清 VLAN 成员。镜像、STP 边缘口与聚合的互斥未验证。
3. 只把**同一规格**的口放进一组：不要把 2.5G 电口和 10G 光口混在一组，除非你明确接受被最慢那条拖住（这也未在本机验证）。
4. 将对端也设为同一模式（两边都静态，或两边都 LACP）。
5. 在本机把这些口的第一列改成 LAG 或 LACP，填同一个非 0 聚合组，再应用、保存。
6. 看 LAG状态、对端状态，以及业务是否还在。有条件就看 LACP PDU。

若管理口就在即将加入聚合的物理口上，先保证另有一条能登录 Web 的路径。

## 和旧工具的关系

GitHub 上有针对 SKS3200-8E2X 的 `swctl` 一类脚本，其 VLAN 模型是「每个端口一组 VLAN + native + 创建 bridge」。
那是给**旧固件**用的。2.0.0.1 没有 Bridge ID 可填，不要把脚本输出直接灌进这一版 Web。
